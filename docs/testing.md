# 测试说明

这份文档说明测试怎么分层、为什么这么分，以及新增功能时应该往哪里加用例。

项目里的测试有一个总原则：**能离线跑的一律离线跑**。调用真实模型既慢又贵，还会因为模型随机性导致测试时好时坏。所以 256 条单元测试全部在 6 秒内跑完，不需要网络、不需要密钥、不需要启动服务。

## 六层验证

| 层次 | 入口 | 覆盖什么 | 需要模型/网络 |
|---|---|---|---|
| 单元测试 | `python -m unittest discover -s code/tests` | 领域计算、工具闸门、路由、限流、脱敏 | 否 |
| 仓库自检 | `python code/scripts/check_repo.py` | 编码、换行、行尾、密钥、必备文件 | 否 |
| 文档校验 | `python code/scripts/check_docs.py` | 文档里的链接、路径、接口、命令是否真实 | 否 |
| 上线预检 | `PYTHONPATH=code/src python code/scripts/preflight.py` | 环境事实：依赖、权限、数据库、密钥、磁盘、备份 | 否 |
| 接口自检 | `PYTHONPATH=code/src python code/scripts/check_confirm_api.py` | 确认状态经 HTTP 读写后是否一致 | 否，但需服务已启动 |
| 端到端 | `python code/examples/demo_agent.py` | 真实模型的完整对话轨迹 | 是 |

前五层进 CI，每次提交都跑；最后一层手动执行，因为它买的是「模型今天表现如何」，不是「代码有没有被改坏」。

接口自检和端到端的分工值得说清楚：`check_confirm_http.py` 要真实模型一路跑到建单才能看到确认卡，额度用完就验不了；`check_confirm_api.py` 直接往库里放一条待确认记录，只用 HTTP 走完「查询 → 确认 → 再查为空 → 重复点击 409」，不依赖模型。前者验的是链路，后者验的是状态机。

## 单元测试的十六个文件

### `tests/test_core.py` —— 钱怎么算

领域层是纯函数，是整个系统里最该被锁死的部分。这里断言的是**绝对数值**，不是「大概相等」：

- `B202610-SF-001` 结论 fail，差额 `4169.61`
- `B202610-ZT-001` 结论 pass，差额 `0`
- `B202609-HD-001` 结论 fail，差额 `540.80`
- `YD2026100104` 应收 `3360.00`，按体积重计费
- `CD2026090203` 不可计入计费重量

这些数字来自业务事实，改代码不应改它们。如果某次重构让这些断言失败了，先怀疑代码，别急着改测试。

### `tests/test_tools.py` —— 闸门有没有守住

工具层测试不调用模型，直接打 `tools.execute()`，验证的是「模型想乱来也乱来不了」：

- 没有 `validation_id` 时调用建单工具，必须被拒
- 争议类型不在枚举里，预检就要拦下，不能等到员工点了确认才报错
- 工具内部抛异常时，返回的是可恢复的错误信封，不是 500
- 每个 skill 引用的工具名，都必须在 `tools.SCHEMAS` 里真实存在

最后一条尤其重要：如果提示词里写了一个不存在的工具名，模型会一直尝试调用它然后失败，而单元测试能提前发现。

### `tests/test_skills.py` —— 路由判对了吗

路由错了会引发两类事故：

- **该进争议流程却被判成制度问答** → 模型看不到核对工具，只能空口回答
- **制度提问被误判成争议流程** → 模型背着十几个工具和几千字流程规则跑，又慢又贵

所以这里正反两个方向都有用例，包括口语倒装（「把账对一下」）、大小写单号、以及「有账期词但没有承运商」这类边界。

### `tests/test_ratelimit.py` 与 `tests/test_utils.py` —— 护栏本身

限流器和脱敏模块是保护机制，保护机制自己出错最危险：

- 限流窗口内第 N+1 次必须被拒，且另一个用户不受影响
- 并发位在异常路径上也必须归还，否则跑几次就永久卡死
- 脱敏要把密钥整段抹掉，但**必须保留金额**——审计需要知道差了多少
- `api_key = os.getenv(...)` 不能被误报成硬编码密钥，否则真问题会被噪音淹没

### `tests/test_prompt.py` —— 补充要求只能追加

后台能改提示词，就必须证明它改不坏硬性规则。这组用例锁三件事：

- 不配置补充要求时，生成的提示词与原来**完全一致**（避免升级悄悄改变线上行为）
- 配置后追加在末尾，且必须带「冲突以硬性规则为准」的声明
- 只填空白字符等同于没配置

### `tests/test_audit.py` —— 审计与清理

这组用例跑在临时数据库上：把 `db.DB_PATH` 指向临时文件、把全局连接置空，测完还原，不碰 `data/runtime/chat.db`。覆盖：

- run 与 steps 的写入、排序、按员工姓名关联
- 状态 / 关键词 / 员工 / 天数四类筛选，以及计数与列表一致
- 统计口径：失败率、工具调用次数与失败次数
- 清理预演不删数据、真清理只删过期行、保留配置能读环境变量且非法值回落 90 天
- 提示词版本的新增、倒序列表、按 id 取全文

### `tests/test_agent_limits.py` —— 预算闸门

执行循环的闸门算错会出两种事故：放太松，模型会反复换关键词查一个制度里根本没有的问题；收太紧，正常的多步核对会被误杀。这组用例验证：

- 检索工具的专项预算到上限就拒绝，且上限必须小于总调用数，否则这道闸永远触发不了
- 其他工具不受专项预算影响
- 确认超时落在 30~600 秒的合理区间
- 准备句过滤器只删「整句无中文 + I'll / Let me 开头」的内容，中文必须立即放行（否则首字延迟会很明显），英文正文不能误删

### `tests/test_confirm.py` —— 确认状态机

这组用例按「两个 worker 的视角」写：一个 worker 创建确认，另一个点确认，等待方只能从库里发现决策。如果哪天有人把状态改回模块级字典，跨进程那几条会立刻失败，而不是等部署两个 worker 后由员工撞上 409。

- 创建后是 `pending`，参数能原样读回
- 确认/取消落到 `confirmed` / `cancelled`，员工改写的正文与操作人都记下来
- 第二次点击被拒，且不能改写第一次的结论
- 越权确认、非法 action、不存在的编号各有明确话术
- 过期的确认点不动，同时被标成 `timeout`，且不再出现在待办列表
- 收尾接口只能写 `timeout` / `abandoned`，不能伪造「已确认」
- 跨进程：本地唤醒表为空时，仍能从库里读到另一个 worker 写入的决策与正文

### `tests/test_config.py` —— 坏配置必须在启动时失败

- 非数字超时、越界配额、非法枚举与 URL 都要被判为 error，且提示里给出可用范围
- 留空的变量等于用默认值，不能报错（`.env` 里注释掉一行是常态）
- 生产模式的五个强制项各有一条：模型密钥、mock 禁止、JWT 密钥长度、Secure Cookie、热重载
- 内网 http 模型地址在 `ALLOW_INSECURE_LLM=1` 时豁免
- 开发模式下 `JWT_SECRET` 缺失只是 warning，不阻断

### `tests/test_http_hardening.py` —— 探针与浏览器侧防线

- `/healthz` 不触碰数据库：依赖全挂也应该 200
- `/readyz` 在索引未加载时返回 503，并逐项给出 `checks`
- 安全头在 HTML 与 JSON 响应上都要有；HSTS 只在 HTTPS（含代理头）下出现
- 跨站 POST 被 403 + 1026 拦住；同源、无 Cookie、`ALLOWED_ORIGINS` 白名单三种情况放行
- 拒绝响应里的 `request_id` 与响应头一致，便于对日志
- 登录回跳只接受站内路径：`//evil.com`、`/\evil.com`、`/%5Cevil.com` 全部拒绝
- `/api/health` 未登录返回 401；响应里不含 `base_url`
- `limit=-1` 返回 422（负数在 SQLite 里等于不限量）
- 上传只读「上限 + 1」字节，即使分块传输拿不到 `file.size`
- 删除文档时 `..`、`.`、`.exe` 一律拒绝，不会变成 500

### `tests/test_backup.py` —— 备份要能用，不只是存在

- 备份是单文件：不能依赖源库的 `-wal`，否则拷走就缺数据
- 备份后核心表行数与源库一致，`integrity_check` 通过
- 保留策略只清理本工具生成的文件，且保留最新的 N 份
- 损坏文件、别家的数据库都要在 `verify` 阶段被拒绝
- 恢复的三个防护：必须 `--yes`、服务在跑时拒绝、覆盖前自动另存当前库

### `tests/test_metrics.py` —— 指标不能把抓取端搞崩

- 标签值里的引号与反斜杠要转义，输出每一行都符合 exposition 格式
- 空路由回退成 `unmatched`，避免高基数
- SSE 计数不会出现负数
- 默认只允许本机；设置 `METRICS_TOKEN` 后才接受 Bearer 或 query token
- `METRICS_ENABLED=0` 时整体关闭

### `tests/test_login_guard.py` —— 锁得住，也要锁得准

登录防爆破最容易写成「要么没用、要么误伤」：阈值太松等于没有，太紧会把正常手误的用户挡在门外。这组用例把两种失败都钉住：

- 同一账号失败到阈值后，**换 IP 也拦**（账号维度独立生效）
- 同一 IP 轮着试不同用户名，**账号维度永不触发**，必须由 IP 维度兜住
- 一个账号被锁不影响同 IP 的其他账号，也不影响其他 IP
- 登录成功清账号计数，但**不清 IP 计数**（否则撒网攻击可以靠自己的合法账号重置）
- 窗口过期后自动解锁，不需要人工干预
- 大量随机用户名不会让内部字典无限增长
- `LOGIN_GUARD_ENABLED=0` 时完全放行（本地调试）

最后一条不是「功能」，而是可关闭性：任何可能挡住合法用户的安全机制，都必须有一个能在事故中立刻关掉的开关，并且这个开关本身要被测试覆盖。

### `tests/test_set_password.py` —— 改完要能登进去

改密看起来只是 `UPDATE users SET password_hash = ?`，但哈希格式是
`pbkdf2_sha256$轮数$盐$哈希`，盐必须随机。手写 SQL 极容易写出一个
「提示改了、登录却失败」的哈希，而这种故障最难排查——日志里一切正常。

- 改密后新口令能通过 `auth.verify_password()`，旧口令失效
- 同一口令两次哈希必须不同（盐随机；相同就说明盐被写死了）
- 不合规口令被拒时，**数据库保持原样**（不能出现改了一半的状态）
- 演示口令单独拦一条：换成 `admin123` 等于没换
- 账号不存在、库不存在都返回退出码 2，而不是抛异常
- `--list` 能正确标出「演示口令（必须更换）」与「已自定义」
- `--generate` 生成的口令必须能通过自己的合规检查

最后一类是「工具检查自己」：生成器与校验器如果标准不一致，
运维会拿到一个当场被自己拒绝的口令。

### `tests/test_bootstrap.py` —— 全新的生产库能不能起来

这组用例对应一个真实存在过的死锁：旧流程无条件播种 `admin/admin123`，
紧接着又因为「仍在使用演示口令」拒绝启动。两段代码各自都「有道理」，
合起来的效果是全新生产库永远起不来，而报错建议的「登录后台改密码」也进不去。

- 开发环境默认播种两个演示账号；生产环境默认不播种
- 生产空库且没配 `ADMIN_INITIAL_PASSWORD` → 拒绝启动，且报错里必须同时出现
  「引导口令」和「`set_password.py`」两条**可执行**路径，`users` 表保持为空
- 配了引导口令 → 建出 `admin`，且哈希能通过 `auth.verify_password()`
- 引导口令本身不合规（比如就是 `admin123`）→ 拒绝，不留半成品账号
- 已有账号时启动是 no-op：绝不把已经改过的口令悄悄改回演示口令
- 引导完成后变量还留在环境里 → 只提示、不覆盖，而且提示文本里不许出现口令值
- 预检对「空库 + 生产 + 无引导口令」判失败，配了则放行

最后两条是配套的：函数层挡住了错误状态，预检层保证它在部署前就被看见。

## 怎么跑

```bash
# 全部单元测试（详细输出）
python -m unittest discover -s code/tests -v

# 单个文件
python -m unittest tests.test_tools -v

# 单个用例
python -m unittest tests.test_core.FreightDomainTests.test_sf_bill_finds_three_planted_errors

# 覆盖率（需要 coverage 包）
python -m coverage run -m unittest discover -s code/tests
python -m coverage report -m
```

## 新增功能时加什么测试

| 你改了什么 | 应该补的测试 |
|---|---|
| `core/domain.py` 的计算逻辑 | `test_core.py`：一个能算出具体数字的正例 + 一个边界（缺价目、单价版本切换） |
| 新增一个工具 | `test_tools.py`：Schema 必填项、成功路径、参数非法时的错误码 |
| 改了路由关键词 | `test_skills.py`：至少一个应该进、一个不应该进 |
| 新增限流维度 | `test_ratelimit.py`：窗口内拒绝、窗口外恢复、多用户隔离 |
| 改了脱敏规则 | `test_utils.py`：要脱敏的必须脱掉，不该动的必须保留 |
| 改了提示词拼接 | `test_prompt.py`：补充要求只能追加，硬性规则必须还在 |
| 新增审计筛选条件 | `test_audit.py`：筛选结果与计数必须一致 |
| 改人工确认的闸门语义 | `test_confirm.py`：越权、重复点击、过期、跨进程唤醒各一条 |
| 调整轮次或工具预算 | `test_agent_limits.py`：上限必须为正且不超过总预算 |
| 新增接口 | `docs/api.md` 补文档，`check_docs.py` 会自动核对 |

## 端到端轨迹回放

`code/examples/demo_agent.py` 会真实调用模型，逐轮打印工具名、参数、耗时和结果摘要，并断言关键约束（比如「只查计费规则”的场景不得调用建单工具）。它适合在以下时机手动跑：

- 改完系统提示词，想确认模型行为没有退化
- 换模型或换供应商后做回归
- 演示前确认链路通畅

```bash
python code/examples/demo_agent.py       # 跑三条
python code/examples/demo_agent.py a     # 只跑第一条
```

## CI 里跑什么

`.github/workflows/ci.yml` 分三个 job：

1. **规范与文档**：ruff 检查 + ruff 格式 + 仓库自检 + 文档校验 + 评测用例
2. **测试**：Python 3.11 / 3.12 / 3.13 三个版本跑同一套单元测试，3.12 额外产出覆盖率
3. **启动冒烟**：无密钥启动服务，验证建表、建索引、挂路由的完整链路，最后请求健康接口

冒烟这一步值得单独说：单元测试全绿但服务起不来是常见事故（比如循环导入、缺少包数据），所以 CI 里必须真的启动一次。
