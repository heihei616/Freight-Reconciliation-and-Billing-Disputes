# 架构与设计

## 1. 设计目标

系统面向结算岗与财务人员，处理制度查询、单票运费计算、整月账单核对与争议草稿。核心原则是：

> **模型负责选择下一步，业务系统负责事实、算术、权限和最终结论。**

这句话决定了整个项目的分层。如果把「算钱」交给模型，它会在第三轮把体积重算错；如果把「能不能建单」交给提示词，它会在用户说「我赶时间」时妥协。所以凡是**错了要赔钱**的判断，都写在确定性代码里。

## 2. 分层与依赖方向

| 层 | 模块 | 职责 | 依赖方向 |
|---|---|---|---|
| Web | `app.py` | 鉴权、页面、SSE、限流、错误信封 | → agent, tools |
| Agent | `agent.py` | 决策循环、轮次预算、人工中断 | → tools, skills |
| 能力包 | `skills.py` | 工具白名单、流程指令、路由、系统提示词 | → tools（只取名字） |
| 工具 | `tools.py` | Schema、参数预检、前置闸门、执行分发、记账 | → domain, db, rag |
| 业务核心 | `core/domain.py` | 运单、账单、价目、额度、凭证、确定性计算 | 不依赖任何上层 |
| 检索 | `rag_service.py`、`reimburse_agent_mvp.py` | 解析、切片、FAISS + BM25 混合召回 | 不依赖业务 |
| 数据 | `db.py` | SQLite 与会话、消息、轨迹、草稿 | → utils/masking |
| 模型 | `llm.py` | OpenAI 兼容流式调用、超时、mock 降级 | 不依赖业务 |
| 横切 | `metrics.py`、`utils/config.py` | 指标采集、启动配置校验 | 不依赖业务，被 `app.py` / `main.py` 调用 |

依赖只允许向下。`core/domain.py` 是纯函数集合，不 import 数据库也不 import 模型——这保证它能被单元测试毫秒级锁死，也保证换模型、换存储都不会动到计算。

横切层是 1.4.0 才拆出来的。原先把配置读取散在各模块里，指标计数塞在路由函数内，结果两件事都做不到可测试：配置校验无法在不起服务的情况下验证，指标也无法断言标签基数。现在两者都是纯函数式的独立模块，`tests/test_config.py` 与 `tests/test_metrics.py` 直接对它们下断言。

## 3. 为什么计算不交给模型

模型很容易在三个地方算错：体积重的抛比、阶梯价的档位、燃油附加费的生效版本。这三种错误在本项目的样例账单里全都真实存在，正是要抓的东西。

因此：

- `compute_freight()` 输出完整推导：计费重量、重量依据、单价、阶梯档、燃油、最低收费、应收金额；
- `validate_bill()` 独立产生 `pass / warn / fail` 与差额，不读模型的说法；
- 模型拿到的只是工具返回值，它没有乘法权限，也不能自己写 verdict。

**争议金额必须等于校验差额**，这条在 `tools.precheck()` 与 `create_dispute_draft` 里各拦一次。员工在确认卡上改金额也不行——改的是正文，不是金额。

## 4. 工具顺序约束

工具不是随便调的，顺序本身就是业务规则：

1. `search_policy` 取得真实 `citation_id`（编造的引用会被校验器识破）；
2. 没给账单号时用 `list_bills` 找，`get_bill_lines` 读取逐行事实；
3. `calc_expected_freight` 算出账单涉及的全部运单；
4. `validate_invoice` 复核事实轨迹与制度引用，发放 `validation_id`；
5. 仅 `fail` / `warn` 可建单，金额必须等于差额；
6. 建单前触发人工确认；提交接口只暴露给员工，**不在模型的工具集里**。

前置条件由服务端回查**自己写的调用轨迹**来强制，不靠提示词。这里有个容易踩的坑：如果记账交给 agent 做，一旦漏记，闸门就会误判成「没做过」。所以 `tools.execute()` 是「谁执行谁记账」，闸门和证据读的是同一份数据。

## 5. 轮次预算与人工中断

| 限制 | 值 | 理由 |
|---|---|---|
| 探索轮上限 | 5 | 整条链实测 4~5 轮，再多基本是在绕圈 |
| 工具调用上限 | 12 | 覆盖并发取数的场景，超过说明模型在原地打转 |
| 同指纹调用上限 | 2 | 同一工具同样参数调第三次一定是循环 |
| 建单收尾轮 | +1 | 5 轮用完但已有校验结论时，白名单只留建单/转人工 |
| 确认等待 | 180 秒 | 短了员工来不及看，长了连接一直挂着 |

人工中断在 `create_dispute_draft` 执行前挂起，SSE 推送 `confirm_open` 与草稿正文，员工点按钮后通过 `POST /api/agent/confirm` 放行同一条流。

**中断状态存在 `pending_confirms` 表，不在进程内存。** 早期版本用 `asyncio.Event` 加一个模块级字典，单 worker 演示没问题，但两点会立刻暴露：

- 负载均衡把确认请求打到另一个 worker，那边的字典里没有这条记录，员工只得到 409；
- 重启服务或页面刷新后，挂起的确认彻底消失，而库里还留着 `awaiting_confirm` 的运行记录。

现在的事件分两条路：同进程写库后顺手 `set()` 本地 Event（零延迟），跨进程由等待方每 0.4 秒读一次 `status`。**唯一事实来源是数据库**，本地字典只当唤醒信号，所以不存在两份状态互相打架。`WHERE status='pending'` 让并发的两次点击只有一个能成功。

中断仍然发生在工具执行之前，不是执行之后。所以即使确认接口被恶意重放，也不会产生第二张草稿——第二次请求拿到 0 行更新，被判成「已处理」。

## 6. 限流、配额与脱敏

这三件事是上线前补的护栏，放在 `ratelimit.py` 与 `utils/masking.py`。

**限流**用滑动窗口而不是固定窗口：固定窗口在整点会出现两倍突发，对模型调用来说就是一瞬间打满配额。

**配额**按自然日分桶，跨天自动归零，不需要定时任务。

**并发闸门**限制的是整个 Agent 循环的并发数，不是 HTTP 请求数——一个 SSE 连接可能占用几十秒，按请求数限流没有意义。

**登录防爆破是另一个桶，不能复用提问限流。** 提问限流按 `user_id` 分，而登录发生时还不知道是谁，只能按「提交的用户名 + 来源 IP」分。两个维度缺一不可：

- 只按 IP：攻击者换代理就能继续打同一个账号；
- 只按账号：一个 IP 轮着试一堆用户名（撞库）永远触发不了账号阈值。

成功登录只清账号计数、不清 IP 计数。这一点反直觉，但必须如此：否则攻击者只要有一个自己的合法账号，登录一次就能重置 IP 桶，撒网攻击不受任何限制。

配套改动是**消除用户名枚举的计时差**。`user is not None and verify_password(...)` 是短路求值：账号不存在时立刻返回，而密码错误要烧掉 20 万次 PBKDF2。两者差几十毫秒，攻击者据此就能判断哪些用户名真实存在。所以账号不存在时也调用 `verify_dummy()` 走一遍同等代价的哈希——这本身是个 CPU 放大面，正好被上面的限流盖住。**两个改动必须一起上**：只加 dummy 哈希，等于把登录接口变成免费的 CPU 消耗器。

**脱敏**放在 `db.py` 的落库收口处，所有调用点自动生效，不依赖每个工具自觉。设计上有三条取舍：

1. 密钥整段抹除，连首尾都不留；
2. 手机号、邮箱、身份证保留结构遮中间，便于排查「是谁的数据」；
3. **金额必须保留**——审计要知道差了多少，抹掉金额等于废掉审计。

扫描器还要放过 `api_key = os.getenv(...)` 与 `client(api_key=api_key)` 这类写法，否则真问题会被误报淹没。这类误报在开发过程中真的出现过，现在由 `tests/test_utils.py` 锁住。

## 7. 可运维性：提示词、审计与日志保留

**提示词只开放「补充」，不开放整段替换。** 硬性规则（金额只能来自工具、无凭证不建单、提交必须人工确认）如果变成可配置项，管理员一次误操作就能把风控删掉；而运营真正需要调的往往只是口径与措辞。所以数据库里 `system_prompt` 存的是补充要求，`skills.build_system_prompt()` 负责内置部分，两段拼接时明确声明「冲突以硬性规则为准」。每次保存写一份 `prompt_revisions` 快照，恢复旧版本本身也记一条，历史不会断。

补充要求每轮请求读一次数据库，不做进程内缓存：后台改完下一次提问就生效，多 worker 也不会各读各的旧值。代价是每次多一次主键查询，相对一次模型调用可以忽略。

**审计按 run / step 两级组织。** `agent_runs` 回答「谁在什么时候问了什么、几轮、多久、成没成」，`agent_steps` 回答「每一轮调了什么工具、参数是什么、卡在哪」。页面只渲染最近 50 条，详情按需拉取，避免一次把几万条轨迹塞进 HTML。所有筛选条件走参数占位符，关键词来自地址栏，拼接就是注入点。

**日志保留只清运行日志。** `agent_runs` / `agent_steps` / `tool_calls` 是「过程记录」，可按天清理；`drafts` / `validations` / `messages` 是「业务留痕」，不清。清理任务放在后台协程，启动先跑一次再每 24 小时一次——长期停机的实例重新拉起时，往往正是日志最需要清的时候；放在请求线程里会锁表卡住 SSE。`LOG_RETENTION_DAYS=0` 关闭自动清理，只保留管理员手动入口。

**两处小加固。** 登录 Cookie 的 `Secure` 默认按请求协议判断，反向代理下读 `X-Forwarded-Proto`，避免 HTTPS 部署时令牌明文传输；本地 http 演示又不会因为强制 Secure 而登录不上。演示账号的播种按环境区分：开发环境照旧建 `admin` / `employee` 以便双击演示，生产环境不播种子——口令随代码发版，进了生产等于后台默认开放。生产的第一个管理员由 `ADMIN_INITIAL_PASSWORD` 引导创建，这个变量在库非空时被忽略并提示移除。生产库若仍留着演示口令，`lifespan` 直接拒绝启动，把「共享环境用弱口令」变成一个立刻失败的动作。

## 8. 知识与数据目录

- `data/knowledge/`：唯一会被索引的目录，只放制度语料；
- `docs/`：项目文档，**不参与检索**——早期把评测文档放在这里，导致制度提问召回示例问答，引用出处指向非制度文档；
- `data/runtime/`：本地 SQLite 与 WAL，已被 `.gitignore` 排除；
- 索引缓存默认在用户主目录，可用 `RAG_INDEX_DIR` 覆盖。

## 9. 错误处理约定

分两个阶段，因为 SSE 的响应头发出后状态码就改不了了：

| 阶段 | 表现 |
|---|---|
| 建流前（参数、鉴权、知识库未就绪、限流） | HTTP 4xx/5xx + JSON 信封 `{code, message, request_id}` |
| 建流后（检索异常、模型超时） | HTTP 仍 200，通过 `event: error` 下发同样的信封 |

错误码分段：1001~1099 请求与鉴权，2001~2099 依赖不可用，3001~3099 流内执行异常。前后端共用同一张表。

工具异常一律转成**可恢复信封**（`code` + `next_hint`），让模型在同一条链路上自己补救，而不是整轮 500。

## 10. 部署形态与可观测性

1.4.0 之前，这套系统的「正确性」有测试兜底，但「出了事能不能被发现、能不能救回来」全靠人记。这一节记录补齐后的三层结构，三层职责不重叠：

| 层 | 产物 | 解决什么 | 明确不负责 |
|---|---|---|---|
| 进程内 | `utils/config.py`、`/healthz`、`/readyz`、`/metrics` | 配置对不对、进程活没活、能不能接流量、当前忙不忙 | 不管重启、不管 TLS |
| 容器 | `Dockerfile`、`docker-compose.yml`、`scripts/backup_db.py` | 一致的运行环境、生命周期与健康判定、数据持久化与可恢复 | 不管多机调度、不管证书 |
| 编排与反代 | nginx / 负载均衡、`scripts/preflight.py` | TLS、超时与缓冲、发布门禁 | 不管业务逻辑 |

### 10.1 启动即校验，而不是启动后告警

配置如果散在几十处 `os.getenv`，最坏的情况不是报错，而是**静默取到默认值**：`LLM_TIMEOUT` 拼错成 `LLM_TIME_OUT`，程序照常启动，直到某天模型卡住 90 秒才有人发现这个值从来没生效过。

所以 `utils/config.py` 把这些收敛成一张规则表——9 个整型带上下界、2 个枚举、若干必填项与强度要求，`validate_env()` 返回 `EnvReport(errors, warnings)`。`main.py` 在 `uvicorn.run()` **之前**跑一次，不通过就打印「哪个变量、当前值、合法范围」，以退出码 2 结束。

放在入口而不是 lifespan 里，是因为 lifespan 抛异常时端口往往已经绑上、日志也已经出现过启动完成的假象，容器编排看到的现象会很混乱。入口退出最干净：非 0 退出码，`restart: unless-stopped` 也不会陷入重启风暴。

同一张规则表被 `scripts/preflight.py` 复用，所以「人手动跑的检查」和「进程启动时的检查」不会各写一套、慢慢漂移。

### 10.2 双探针：把「活着」和「能干」分开

把就绪检查配成存活探针是最常见的部署事故：数据库抖一下，编排层认为进程死了，全部重启；重启期间请求继续失败，于是再重启一轮，小抖动被放大成雪崩。

| 端点 | 语义 | 检查内容 | 失败时编排层该做什么 |
|---|---|---|---|
| `/healthz` | 进程还活着 | 只回 uptime 与 version，不碰任何 IO | 重启容器 |
| `/readyz` | 现在能不能接流量 | `SELECT 1` + 文档数与切片数 + 模型配置 | 摘掉流量，**不**重启 |

`/readyz` 的响应体带实测值（数据库耗时与体积、文档数、切片数、provider/model），排障时不用先登上服务器。两个端点都不鉴权、不触发模型调用、不写业务日志——探针每 30 秒打一次，写日志会把审计表冲垮。

### 10.3 指标：零依赖，但必须控制基数

`metrics.py` 自己输出 Prometheus 文本格式，没有引入 `prometheus_client`。理由很实际：为了几十行文本加一个依赖，还要跟着它的版本改初始化方式，不划算；自实现反而能精确控制标签。

标签基数是这里唯一容易埋雷的地方。`route` 必须用**路由模板**而不是原始路径，否则 `/api/agent/runs/{run_id}` 每来一个请求就长出一条新时间序列，一周就能把 Prometheus 打爆。所以中间件取的是 `request.scope["route"].path`，取不到时统一归到 `<unmatched>`，而不是退化成原始 URL。

指标默认只允许本机读取（同机采集或 sidecar），跨机采集要配 `METRICS_TOKEN`。`METRICS_ENABLED=0` 直接 404，不给探测者留下「这里有内部指标」的信号。

### 10.4 备份：不能用 cp

WAL 模式下直接 `cp chat.db` 得到的可能是一个缺少最近提交的文件，而且旁边还躺着 `-wal`，很容易被当成「备份完整」收进归档。真到恢复时才发现少了几小时数据。

`scripts/backup_db.py` 走 SQLite 的在线 `backup()` API，完成后 `wal_checkpoint(TRUNCATE)` 并把 `journal_mode` 切回 `DELETE`，保证产物是**单文件**——这一点有测试锁着（`test_backup_file_is_standalone`）。`verify` 做 `integrity_check` 并比对各表行数，`create` 之后自动清理超出保留份数的旧备份。

恢复比备份危险得多，所以加了四道闸：必须显式 `--yes`、检查 8000 端口没有实例在跑、先把当前库另存为 `chat-before-restore-*.db`、恢复后立刻 `integrity_check`。先删 `-wal` / `-shm` 再恢复，否则旧 WAL 会在下次打开时把数据盖回去——这个坑在演练时真实踩到过。

### 10.5 容器：三处容易漏的细节

多阶段构建，builder 装依赖、runtime 只带 venv 与源码。三个细节值得记下来：

1. **`libgomp1` 必须显式装**。它是 FAISS / onnxruntime 的运行时依赖，缺了不会构建失败，而是在 `import` 那一刻崩——错误信息还指向无关的位置。这类问题在本地开发机上永远不会出现，因为开发机早就有了。
2. **`HEALTHCHECK` 打 `/healthz` 而不是 `/readyz`**。理由同 10.2：健康检查触发的是重启，不能让它被下游抖动带偏。
3. **`stop_grace_period: 30s`**。uvicorn 收到 SIGTERM 后先停止接收新连接，再等在途 SSE 收尾。默认 10 秒会直接把正在生成回答的流掐断，用户看到的是「回答到一半没了」。

容器以 UID 10001 非 root 运行，端口只绑 `127.0.0.1`，TLS 与鉴权边界交给前面的反代。

### 10.6 反代三个必改项

默认配置能跑通普通 HTTP，但会在这三处让 SSE 出问题：

| 配置 | 默认值的后果 | 正确做法 |
|---|---|---|
| `proxy_buffering` | 开着时 nginx 攒够缓冲区才下发，SSE 变成「等十几秒然后一次性出现」 | `off` |
| `proxy_read_timeout` | 60s 会掐断 180s 的人工确认等待 | ≥ 300s |
| `X-Forwarded-Proto` | 不透传时后端以为是 http，Cookie 不加 `Secure`、HSTS 也不发 | 透传，并把 `FORWARDED_ALLOW_IPS` 设为反代地址而非 `*` |

`FORWARDED_ALLOW_IPS=*` 看似省事，实际是让任何客户端都能伪造来源 IP 与协议，限流按 IP 分桶时会直接被绕过。

## 11. 验证策略

| 手段 | 覆盖 |
|---|---|
| 256 条单元测试 | 金额、闸门、路由、限流、脱敏、确认状态机、配置校验、HTTP 加固、备份、指标、凭据轮换、登录防爆破、首次引导，全部离线 |
| `scripts/check_gates.py` | 绕过模型直接攻击工具闸门，8 场景 16 项断言 |
| `scripts/check_confirm_api.py` | 不调模型，用 HTTP 验证确认状态机，11 项断言 |

七个新增测试文件各自锁一类「以前只能靠人记」的东西：`test_config.py` 锁配置边界（26 条）、`test_http_hardening.py` 锁 CSRF、安全头、登录跳转与上传边界（24 条）、`test_backup.py` 锁备份单文件与恢复语义（9 条）、`test_metrics.py` 锁指标格式与标签基数（13 条）、`test_set_password.py` 锁「改完能被登录逻辑认出来」（19 条）、`test_login_guard.py` 锁「锁得住也锁得准」（10 条）、`test_bootstrap.py` 锁「全新的生产库能起来且不播种弱口令」（15 条）。这些都不是业务逻辑，但都是上线后才暴露、暴露时已经造成损失的那类问题。

设计文档最容易腐化，所以它自己也被校验：`check_docs.py` 会把本文里的接口和路径拿去和代码对一遍。

## 12. 已知限制

这些限制是**明确接受**的，不是遗漏：

1. **限流计数在单进程内存**：确认状态已经搬进数据库，但限流还没有。多实例部署时限额是「每实例」而不是「每用户」，实际额度会被放大 N 倍。登录失败计数同样如此——两个实例意味着攻击者每个账号能试 10 次而不是 5 次。真要横向扩展，下一步是把 `ratelimit` 的计数器换到 Redis。
2. **SQLite 单写入锁**：适合小团队（3~5 人），并发写靠全局锁串行化，人多了要换 PostgreSQL。确认等待是 0.4 秒一次的读，不占写锁，所以挂着几十个确认也不会拖慢聊天。
3. **演示账号仍在代码里**：`admin/admin123`、`employee/emp123` 的口令写死在 `auth.py`，这样「双击就能演示」不依赖任何手工步骤。代价是**仓库里始终存在一份可用口令**，所以播种只发生在非生产环境；生产改用 `ADMIN_INITIAL_PASSWORD` 引导，且该口令要过与命令行改密同一套强度规则。彻底去掉这份字面量的做法是「开发也走引导」，但那会让新克隆的仓库必须先配一个环境变量才能登录，对演示场景不划算。
4. **跨进程唤醒最多延迟 0.4 秒**：另一个 worker 点确认后，等待方靠轮询发现，没有消息广播。人感知不到，但如果将来要接多实例事件总线，这里是替换点。
5. **确认卡不会在多个标签页之间自动收起**：状态在库里，刷新或切换会话会重建；但已经打开的另一个标签页不会实时收到「已处理」通知，除非它还连着原 SSE 流。
6. **`pending_confirms` 只增不删**：和审计日志一样，保留原样便于复盘。表很窄，一年几万行对 SQLite 没有压力；要清理可按 `decided_at` 自行加策略。
7. **镜像未在真实 Docker 环境构建过**：`Dockerfile` 与 `docker-compose.yml` 已做静态校验（`check_repo.py` 会核对 `COPY` 源路径存在且未被 `.dockerignore` 排除），但开发机没有 Docker，镜像没有实跑。首次部署必须以 `docs/prelaunch_checklist.md` 6.5 的验收结论为准，不能因为「文件都在」就认为能跑。
8. **指标是进程内聚合**：多实例部署时每个实例各自暴露 `/metrics`，跨实例汇总由 Prometheus 侧按 `instance` / `job` 完成，系统本身不做汇总，也不做告警判定。告警规则需要运维侧另配。
9. **预检只做静态与只读检查**：`preflight.py` 不会真的发一次模型请求，也不会启动服务。它能发现「密钥没配」「数据库损坏」「端口被占」，但发现不了「密钥配了但已过期」。上线前仍需人工跑一次真实问答。
10. **改密不会让已签发令牌立刻失效**：JWT 是无状态的，`user_from_request()` 只验签名与有效期，不查库。所以改完口令后，旧令牌最长还能用 `JWT_EXPIRE_HOURS`（默认 8 小时）。要立即踢下线只能轮换 `JWT_SECRET`，代价是所有人重新登录。如果将来需要「单独踢掉某个用户」，得在令牌里加一个按用户递增的版本号，并在每次请求时比对——那是一次读库，与现在「鉴权不碰数据库」的取舍相反。
11. **账号停用没有界面入口**：`users.is_active` 字段存在且登录会校验，但目前只能改库。人员离职场景建议先轮换 `JWT_SECRET`（立即失效）再改库停用账号。
