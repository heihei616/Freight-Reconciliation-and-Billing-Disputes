# 架构与设计

## 1. 设计目标

系统面向结算岗与财务人员，处理制度查询、单票运费计算、整月账单核对与争议草稿。核心原则是：

> **模型负责选择下一步，业务系统负责事实、算术、权限和最终结论。**

这句话决定了整个项目的分层。如果把「算钱」交给模型，它会在第三轮把体积重算错；如果把「能不能建单」交给提示词，它会在用户说「我赶时间」时妥协。所以凡是**错了要赔钱**的判断，都写在确定性代码里。

## 2. 分层与依赖方向

| 层 | 模块 | 职责 | 依赖方向 |
|---|---|---|---|
| Web | `app.py` | 鉴权、页面、SSE、限流、错误信封 | → agent, tools |
| Agent | `agent.py` | 决策循环、轮次预算、人工中断 | → tools, skills |
| 能力包 | `skills.py` | 工具白名单、流程指令、路由、系统提示词 | → tools（只取名字） |
| 工具 | `tools.py` | Schema、参数预检、前置闸门、执行分发、记账 | → domain, db, rag |
| 业务核心 | `core/domain.py` | 运单、账单、价目、额度、凭证、确定性计算 | 不依赖任何上层 |
| 检索 | `rag_service.py`、`reimburse_agent_mvp.py` | 解析、切片、FAISS + BM25 混合召回 | 不依赖业务 |
| 数据 | `db.py` | SQLite 与会话、消息、轨迹、草稿 | → utils/masking |
| 模型 | `llm.py` | OpenAI 兼容流式调用、超时、mock 降级 | 不依赖业务 |

依赖只允许向下。`core/domain.py` 是纯函数集合，不 import 数据库也不 import 模型——这保证它能被单元测试毫秒级锁死，也保证换模型、换存储都不会动到计算。

## 3. 为什么计算不交给模型

模型很容易在三个地方算错：体积重的抛比、阶梯价的档位、燃油附加费的生效版本。这三种错误在本项目的样例账单里全都真实存在，正是要抓的东西。

因此：

- `compute_freight()` 输出完整推导：计费重量、重量依据、单价、阶梯档、燃油、最低收费、应收金额；
- `validate_bill()` 独立产生 `pass / warn / fail` 与差额，不读模型的说法；
- 模型拿到的只是工具返回值，它没有乘法权限，也不能自己写 verdict。

**争议金额必须等于校验差额**，这条在 `tools.precheck()` 与 `create_dispute_draft` 里各拦一次。员工在确认卡上改金额也不行——改的是正文，不是金额。

## 4. 工具顺序约束

工具不是随便调的，顺序本身就是业务规则：

1. `search_policy` 取得真实 `citation_id`（编造的引用会被校验器识破）；
2. 没给账单号时用 `list_bills` 找，`get_bill_lines` 读取逐行事实；
3. `calc_expected_freight` 算出账单涉及的全部运单；
4. `validate_invoice` 复核事实轨迹与制度引用，发放 `validation_id`；
5. 仅 `fail` / `warn` 可建单，金额必须等于差额；
6. 建单前触发人工确认；提交接口只暴露给员工，**不在模型的工具集里**。

前置条件由服务端回查**自己写的调用轨迹**来强制，不靠提示词。这里有个容易踩的坑：如果记账交给 agent 做，一旦漏记，闸门就会误判成「没做过」。所以 `tools.execute()` 是「谁执行谁记账」，闸门和证据读的是同一份数据。

## 5. 轮次预算与人工中断

| 限制 | 值 | 理由 |
|---|---|---|
| 探索轮上限 | 5 | 整条链实测 4~5 轮，再多基本是在绕圈 |
| 工具调用上限 | 12 | 覆盖并发取数的场景，超过说明模型在原地打转 |
| 同指纹调用上限 | 2 | 同一工具同样参数调第三次一定是循环 |
| 建单收尾轮 | +1 | 5 轮用完但已有校验结论时，白名单只留建单/转人工 |
| 确认等待 | 180 秒 | 短了员工来不及看，长了连接一直挂着 |

人工中断在 `create_dispute_draft` 执行前挂起，SSE 推送 `confirm_open` 与草稿正文，员工点按钮后通过 `POST /api/agent/confirm` 放行同一条流。

**中断状态存在 `pending_confirms` 表，不在进程内存。** 早期版本用 `asyncio.Event` 加一个模块级字典，单 worker 演示没问题，但两点会立刻暴露：

- 负载均衡把确认请求打到另一个 worker，那边的字典里没有这条记录，员工只得到 409；
- 重启服务或页面刷新后，挂起的确认彻底消失，而库里还留着 `awaiting_confirm` 的运行记录。

现在的事件分两条路：同进程写库后顺手 `set()` 本地 Event（零延迟），跨进程由等待方每 0.4 秒读一次 `status`。**唯一事实来源是数据库**，本地字典只当唤醒信号，所以不存在两份状态互相打架。`WHERE status='pending'` 让并发的两次点击只有一个能成功。

中断仍然发生在工具执行之前，不是执行之后。所以即使确认接口被恶意重放，也不会产生第二张草稿——第二次请求拿到 0 行更新，被判成「已处理」。

## 6. 限流、配额与脱敏

这三件事是上线前补的护栏，放在 `ratelimit.py` 与 `utils/masking.py`。

**限流**用滑动窗口而不是固定窗口：固定窗口在整点会出现两倍突发，对模型调用来说就是一瞬间打满配额。

**配额**按自然日分桶，跨天自动归零，不需要定时任务。

**并发闸门**限制的是整个 Agent 循环的并发数，不是 HTTP 请求数——一个 SSE 连接可能占用几十秒，按请求数限流没有意义。

**脱敏**放在 `db.py` 的落库收口处，所有调用点自动生效，不依赖每个工具自觉。设计上有三条取舍：

1. 密钥整段抹除，连首尾都不留；
2. 手机号、邮箱、身份证保留结构遮中间，便于排查「是谁的数据」；
3. **金额必须保留**——审计要知道差了多少，抹掉金额等于废掉审计。

扫描器还要放过 `api_key = os.getenv(...)` 与 `client(api_key=api_key)` 这类写法，否则真问题会被误报淹没。这类误报在开发过程中真的出现过，现在由 `tests/test_utils.py` 锁住。

## 7. 可运维性：提示词、审计与日志保留

**提示词只开放「补充」，不开放整段替换。** 硬性规则（金额只能来自工具、无凭证不建单、提交必须人工确认）如果变成可配置项，管理员一次误操作就能把风控删掉；而运营真正需要调的往往只是口径与措辞。所以数据库里 `system_prompt` 存的是补充要求，`skills.build_system_prompt()` 负责内置部分，两段拼接时明确声明「冲突以硬性规则为准」。每次保存写一份 `prompt_revisions` 快照，恢复旧版本本身也记一条，历史不会断。

补充要求每轮请求读一次数据库，不做进程内缓存：后台改完下一次提问就生效，多 worker 也不会各读各的旧值。代价是每次多一次主键查询，相对一次模型调用可以忽略。

**审计按 run / step 两级组织。** `agent_runs` 回答「谁在什么时候问了什么、几轮、多久、成没成」，`agent_steps` 回答「每一轮调了什么工具、参数是什么、卡在哪」。页面只渲染最近 50 条，详情按需拉取，避免一次把几万条轨迹塞进 HTML。所有筛选条件走参数占位符，关键词来自地址栏，拼接就是注入点。

**日志保留只清运行日志。** `agent_runs` / `agent_steps` / `tool_calls` 是「过程记录」，可按天清理；`drafts` / `validations` / `messages` 是「业务留痕」，不清。清理任务放在后台协程，启动先跑一次再每 24 小时一次——长期停机的实例重新拉起时，往往正是日志最需要清的时候；放在请求线程里会锁表卡住 SSE。`LOG_RETENTION_DAYS=0` 关闭自动清理，只保留管理员手动入口。

**两处小加固。** 登录 Cookie 的 `Secure` 默认按请求协议判断，反向代理下读 `X-Forwarded-Proto`，避免 HTTPS 部署时令牌明文传输；本地 http 演示又不会因为强制 Secure 而登录不上。演示口令在启动时做一次校验并告警——不阻断启动（课程验收要用这两个账号），但把风险写在日志第一屏。

## 8. 知识与数据目录

- `data/knowledge/`：唯一会被索引的目录，只放制度语料；
- `docs/`：项目文档，**不参与检索**——早期把评测文档放在这里，导致制度提问召回示例问答，引用出处指向非制度文档；
- `data/runtime/`：本地 SQLite 与 WAL，已被 `.gitignore` 排除；
- 索引缓存默认在用户主目录，可用 `RAG_INDEX_DIR` 覆盖。

## 9. 错误处理约定

分两个阶段，因为 SSE 的响应头发出后状态码就改不了了：

| 阶段 | 表现 |
|---|---|
| 建流前（参数、鉴权、知识库未就绪、限流） | HTTP 4xx/5xx + JSON 信封 `{code, message, request_id}` |
| 建流后（检索异常、模型超时） | HTTP 仍 200，通过 `event: error` 下发同样的信封 |

错误码分段：1001~1099 请求与鉴权，2001~2099 依赖不可用，3001~3099 流内执行异常。前后端共用同一张表。

工具异常一律转成**可恢复信封**（`code` + `next_hint`），让模型在同一条链路上自己补救，而不是整轮 500。

## 10. 验证策略

| 手段 | 覆盖 |
|---|---|
| 140 条单元测试 | 金额、闸门、路由、限流、脱敏、确认状态机，全部离线 |
| `scripts/check_gates.py` | 绕过模型直接攻击工具闸门，8 场景 16 项断言 |
| `scripts/check_confirm_api.py` | 不调模型，用 HTTP 验证确认状态机，11 项断言 |
| `scripts/check_docs.py` | 文档里的链接、路径、接口、命令是否真实存在 |
| `tests/data/eval_cases.json` | 30 条评测用例：制度 / 工具 / 违规意图 / 多轮 |
| `examples/demo_agent.py` | 真实模型回放三条典型轨迹 |

设计文档最容易腐化，所以它自己也被校验：`check_docs.py` 会把本文里的接口和路径拿去和代码对一遍。

## 11. 已知限制

这些限制是**明确接受**的，不是遗漏：

1. **限流计数在单进程内存**：确认状态已经搬进数据库，但限流还没有。多实例部署时限额是「每实例」而不是「每用户」，实际额度会被放大 N 倍。真要横向扩展，下一步是把 `ratelimit` 的计数器换到 Redis。
2. **SQLite 单写入锁**：适合小团队（3~5 人），并发写靠全局锁串行化，人多了要换 PostgreSQL。确认等待是 0.4 秒一次的读，不占写锁，所以挂着几十个确认也不会拖慢聊天。
3. **演示口令随代码发版**：`admin/admin123`、`employee/emp123` 仅供本地，生产必须换。
4. **跨进程唤醒最多延迟 0.4 秒**：另一个 worker 点确认后，等待方靠轮询发现，没有消息广播。人感知不到，但如果将来要接多实例事件总线，这里是替换点。
5. **确认卡不会在多个标签页之间自动收起**：状态在库里，刷新或切换会话会重建；但已经打开的另一个标签页不会实时收到「已处理」通知，除非它还连着原 SSE 流。
6. **`pending_confirms` 只增不删**：和审计日志一样，保留原样便于复盘。表很窄，一年几万行对 SQLite 没有压力；要清理可按 `decided_at` 自行加策略。
